# 看一个 agent 项目要关注什么

## 高区分度（值得花 80% 时间）

### 1. 上下文的进出策略

这是我认为唯一最重要的一项。具体问：

- 第 N 轮的 context 里到底有什么？完整历史、滑动窗口、摘要、还是重建的？
- 工具输出怎么进 context？全文塞进去 / 截断 / 落盘只回一个路径让 agent 自己去 grep？（最后这种是个大 idea：把文件系统当外部状态，context 只存指针）
- 压缩由谁触发？外部启发式（超过 X token 就摘要）还是模型自己决定写什么、丢什么？
- prompt 前缀稳不稳定？不稳定 = cache 全废，成本和延迟差一个数量级。这条几乎没人在 README 里写，但看主循环就知道。

### 2. 反馈信号是不是真的

决定 agent 能否自我纠错的是有没有**外部 ground truth**：编译器、类型检查器、测试、schema 校验、真实 API 的报错。

- 有 verifier 的项目，agent 循环有意义。
- 只有 LLM-as-judge 自评的项目，循环基本是在放大自己的幻觉——多跑几轮不会更好。
- 还要看反馈延迟：每步都有，还是只有终局才知道对错。后者几乎必然失败。

### 3. 动作空间的粒度

- 一个 `bash` + 一个文件编辑，还是 47 个细粒度工具？前者依赖模型能力，后者依赖设计者的先验，两条路都有人成功，但选择本身透露了作者对模型能力的判断。
- 有没有用**代码作为动作**（让模型写 Python 而不是发 JSON）？这能一次表达循环、条件、组合，是个真实的表达力跃升。
- 错误信息是不是当 prompt 在写？`Error: invalid input` 和 `Error: 'date' must be ISO-8601, got '3/4/25'. Did you mean '2025-03-04'?` 是两个项目。

### 4. 停止与预算

- 终止判据：模型自己说完成 / verifier 通过 / 状态机到终态 / 预算耗尽兜底？
- 有没有**无进展检测**？连续 K 轮没改变状态就中断，这个几乎所有能用的 agent 都有，所有 demo 项目都没有。
- 有没有 replan 触发条件，还是撞墙了就一直撞？

### 5. 状态放在哪

agent 对世界的认知是纯粹活在 context 里，还是有外部载体（文件、git、DB、todo list）？

- 外部载体 = 可检查、可恢复、可被人接手、可跨 context 窗口。
- 纯 context = 崩了就没了，窗口满了就失忆。

这条基本能预测项目能不能跑长任务。

## 中等区分度

### 6. 控制流的自主度

硬编码 workflow（DAG/状态机）↔ 完全自主循环，是一条谱。看它落在哪，以及作者有没有意识到这是个权衡。声称"完全自主"但实际 prompt 里写了 12 步流程的项目很多。

### 7. 跨会话记忆的写入侧

大部分项目的记忆设计都只想了检索（embedding + 向量库，零信息量），值得看的是**写入**：

- 什么时候写？谁决定写？
- 写的粒度是原始对话片段还是提炼后的结论？
- 冲突和过期怎么处理——旧记忆说 A，新观察说 not A，谁赢？
- 有没有遗忘机制？

只有检索没有写入策略的记忆系统，等于一个会越来越脏的缓存。

### 8. 多 agent 分解的理由

不看它分了几个，看它**为什么分**。合法理由只有三个：context 隔离（子任务的中间垃圾不污染主线）、真并行、权限隔离。如果理由是"模拟一个软件公司"、"CEO agent 指挥 PM agent"，这是拟人化，不是架构。

还要看：通信是共享黑板还是消息传递？谁合并结果、冲突怎么裁决？

### 9. 并行与调度

哪些工具调用能并发发出？有没有 speculative 执行？模型分层路由（便宜模型干什么）？这块跟你熟的东西同构——本质是在算依赖图、找关键路径、隐藏延迟。做得好的项目在这里会有明显痕迹。
